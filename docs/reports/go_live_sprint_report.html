The rule that now separates them

A regulatory failure withholds the regulatory artefact and nothing else. A dwelling type the regulator has no code for does not make the lender's balances wrong, so the management report is still offered for approval and the published record carries no XML reference. D

Mapping governance

Three defects stood between an operator's answer and the data. All three are closed.

What was wrongWhy it matteredNow
The Review Centre said "All fields were matched using your approved rules" whenever Gate 1's step completed. A completed step means Gate 1 finished, not that the mapping is settled. On Client A's first delivery that sentence was untrue 40 times over, and no decisions were raised at all — so Gate 2 refused a package nobody had been asked to fix. The stage reports the handoff manifest's own numbers and offers the queue Gate 1 built.
"Point it at a column in the files" was offered, but there was nowhere to put the column name — and the option named an action (map_source_column) the apply step does not support. Approving it recorded an answer that applied to nothing. The operator saw an accepted decision and an unchanged canonical. The decision API carries the column; the options name actions the engine executes; the single-file delivery supplies its own filename, and a multi-file pack is asked rather than guessed.
Rerun resumed from persisted state and skipped completed steps. Approved decisions are applied by Gate 1, so its previous output is stale the moment they change. Every answer was silently discarded. The run tracks the digest of the approved-decisions artefact Gate 1 last consumed and reproduces Gate 1, and everything downstream of its tape, when it differs.

The operator's five actions

  • Accept the proposal as offered.
  • Change it — choose a different treatment.
  • Point it at a column — name the source column the field lives in.
  • Mark not applicable — this book does not hold it.
  • Defer — record that you are waiting on the lender. The item stays open and the run stays held, so deferring can never be a quiet way to make a blocking question disappear.

The LLM stays a recommender

Both rehearsals ran with the resolver off. The Part II benchmark measured it at 75% precision against the deterministic matcher's 100%, and — worse — it drove blocking decisions to zero, so its three false positives, one of them on a balance, would have reached MI with no human ever seeing them. The policy machinery is wired and OCC resolves it correctly; the recommendation is that TRAKT_LLM_MODE=resolving stays off in production and the arm is used for advice a person confirms.

The lender's own words survive

"Probate — awaiting sale" is a real servicing state. ESMA has no code for it and management information depends on it. It reaches MI exactly as written.

Strict enum conformance belongs at the regulatory boundary, and that is where it now lives. Where ESMA requires a permitted code, the translation is a governed decision recorded once at client scope and reused; the management value it translates is unchanged by it. Where no translation exists, the regulatory branch holds and the management report does not.

Why this is worth the words

The alternative — nulling a value the regulator does not recognise — is the kind of defect that is invisible until someone asks why the probate book looks empty. Three tests now assert the exact string survives Gate 2, Gate 3 and assembly, and that an unknown enum is not a blocking validation error.

Client isolation

What was found

The Annex 2 delivery chain read config/client/config_client_ERM_UK.yaml for every client. That is one existing client's file, so every other lender's regulatory identity — LEI, originator name, establishment country — was assessed against someone else's. Client B's valid LEI was reported as invalid because the check was never looking at it.

The effective-configuration resolver already resolved a client's own generated configuration correctly. The delivery chain simply was not using it. It does now.

K

The routing fix, and what it left

Historical — the routing fix stands, what it left does not

The routing defect and its fix are current and unchanged: regulatory-only columns survive onboarding, and that is permanent. What this section describes as remaining — the XML still blocked, one field discovered per round — is superseded by section O, which found that the fields were not the problem.

The defect was general: OCC classified a regime-required delivery correctly and then asked Gate 1 to grade it against the management contract, which excludes the regulatory category outright. Every regulatory-only column a lender supplied was discarded during onboarding.

What changed

The routing now derives from the rule that already knew the answer. select_target maps dataset plus regime_required to a target; a target other than mi means this delivery owes a regulatory return. That single answer is threaded to the three places that resolve scope independently — Gate 1's field scope, the central tape builder's, and the target contract, which is extended with the regulatory targets renamed from the existing Annex 2 contract, so each keeps the dispositions the regime rules already define: its default, its permitted ND codes, its derivation. Not a second regulatory mapper — a rename of the one that exists.

field scope, MI contract, regime-required delivery included fields 159 → 414 what Gate 1 is willing to see blocking fields 11 → 13 what a lender is required to supply Scope moved. Requirements did not.

That distinction is the whole safety argument. Every added target is optional and non-enforcing, so no ESMA field becomes a mandatory lender source. Gate 1 still distinguishes source-mapped, derived, configured, defaulted, ND-eligible, not applicable and genuinely missing. And the canonical keeps management semantics, because the contract is still the MI one — Client B's account_status still reaches MI as "Probate - awaiting sale".

Three defects the fix exposed, and closed

Each was only reachable once regulatory fields were actually in the canonical, which is a fair description of why they had never been seen.

  • An ND code is a string, and the regulator asks for it in numeric fields too. Writing "ND1" into a column pandas had typed Int64 raised TypeError and failed Gate 2 outright. The column is widened first; the value is never coerced.
  • A regulatory-only field that is absent was blocking validation, taking otherwise valid management data down with it. Whose mandatory decides which branch: a core field makes the canonical wrong and blocks validation; a regulatory-only one makes the return wrong and blocks projection, leaving MI publishable.
  • An enum map is a projection instruction, not a configured value. Copied verbatim it dispositioned a field as "configured static" with nothing to configure — no column, and a projection that then rejected the field it had been told was handled.

What still stops the XML

What happens. The projection now clears property_type and stops on purpose (RREL27): the lender's tape has no purpose column, and ESMA will not accept an empty value in an enum field.

Why it is not the same blocker. The previous one was information being destroyed — a column the lender supplied, discarded before anyone could use it. This one is information the lender never supplied. That is a legitimate thing for a system to stop on.

Why it still stops. ESMA permits ND5 here, but the regime rules define no default for it, so Gate 1 dispositions it needs_confirmation — correctly — and nobody is asked, because it is optional and non-blocking for MI. The operator therefore has no route to say "record it as not collected". A decision surface exists for a regulatory enum whose values are wrong; there is none for one whose values are absent.

The shape of the fix. Raise the ND choice as a decision at the projection boundary, offering the codes the regime rules already permit, and persist the answer as the configured value for that target — the existing configure_static_value bridge, which already carries an operator's amendment into the next Gate 1 run. It is a decision surface, not an engine change, and it is the last thing between this pipeline and an XML return.

I did not build it here. It is a different defect from the one this sprint was scoped to fix, the instruction was not to broaden the work, and a change of that shape made at the end of a long session without its own rehearsal is exactly the kind that looks finished and is not.

Three fixes the surface made reachable

  • An empty column is not an unmapped value. Only "NAN" was excluded from the check, so a regulatory column the lender does not supply was reported as data failing the regulator's code list — and strict mode refused the whole return over it. How a blank stringifies depends on the column's dtype.
  • A no-data default only filled gaps in a column that already existed, which is the one case it is not needed. An absent column is what a no-data code is for.
  • Two identifiers had no derivation. The field map gives RREC1 the same canonical field as RREL1, and ESMA says to report the same identifier when it has not changed — so the original-from-new backfills now match the new-from-original ones that already existed.

N

Who owns the equity release configuration

First, a correction to the brief's premise

There is no config_ERM_UK.yaml. The repository contains config/client/config_client_ERM_UK.yaml (and a _demo twin), and its own first line calls it "LAYER 3: MASTER CLIENT CONFIG". It is a client file.

The reusable UK equity release product layer is a different file that already exists: config/asset/product_defaults_ERM.yaml, Layer 2, with 22 no-data treatments and 10 product defaults. It is alive, authoritative, and — until this commit — never reached Gate 4.

E. Gate 4 / Gate 5 reconciliation

The invariant, and what it took to state it correctly

Gate 5 does not read a code's multiplicity across every branch. It selects an XML branch for the value in hand and reads that branch's minOccurs — so a code with an optional branch somewhere is still refused when the branch chosen for an empty value is [1..1]. Taking the minimum across all branches, which is the obvious reading, made Gate 4b call such a field optional and hand Gate 5 a frame it refused. The contract now computes mandatory-ness exactly as the builder does.

It also matches the builder's other asymmetry: an absent column is skipped, a present-and-blank column is refused. So presence is not enforced, and a value — where the column exists — is.
